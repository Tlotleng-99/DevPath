When things go wrong, have a plan B

🔌 Load Shedding Survival

Code fails. A good program expects that failure, catches it, and carries on with plan B — like Eskom dipping the lights on you.

Try it yourself live

You need to charge the phone, but the grid might cut the lights. Each attempt asks: try it... and if it fails, catch it and switch to the power bank.

📱🔋
Ready to try charging…
try:
    charge_phone()              # risky!
except LoadSheddingError:
    switch_to_power_bank()      # plan B, phone saved

The proper cs name

An exception is an error raised at runtime. If you don't catch it, the program crashes. If you do — it recovers and keeps living.

  • try: — put the risky work here.
  • except SomeError: — catch exactly that problem.
  • finally: — cleanup that always runs.
try:
    phone = charge(phone)
except LoadSheddingError:
    phone = charge_from(power_bank)   # plan B
except BatteryExplosion:
    run()                              # plan C 🏃
else:
    celebrate()                        # no errors 👍
finally:
    unplug_stuff()                     # always runs

Where they live: opening files that may not exist, reading network data, user input that is garbage, dividing by zero. Robust code is code that catches.

The story, slowly 🧠

1

Things go wrong — yoh

Load shedding strikes. Your code hits an error it didn't ask for. Untreated, the whole program crashes like a blackout.

2

Try the risky thing

You put the risky step inside try. The program attempts it and watches closely — it doesn't jump ship at the sign of trouble.

3

Except catches it

If the error appears, the except block grabs it and switches to plan B: power bank. The program keeps running instead of dying.

4

Crash-proofing

Real-world code is full of try/except — bad files, flaky internet, human typos. Good devs design for failure: they expect load shedding.
