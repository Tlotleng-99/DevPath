Blueprint → real things

🚐 The Kombi Blueprint

The class is the blueprint; each real kombi is an object with its own colour, route, and a hooter that works.

Try it yourself live

Build kombis from the Kombi class. Each one you build is its own object: pick colour and route, then hooter() and drive() on that kombi only.

class Kombi:
    def __init__(self, colour, route):
        self.colour = colour
        self.route = route
    def hooter(self):
        return "Phiphi! 🚐"
    def drive(self):
        return "ka-chow, moving!"

The proper cs name

Object-oriented programming bundles data (attributes) and behaviour (methods) into one unit — an object, made from a class blueprint.

  • Class = the blueprint (never drives anywhere).
  • Object = a real instance built from it.
  • Attributes = state: colour, route, seats.
  • Methods = behaviour: hooter(), drive().
class Kombi:
    def __init__(self, colour, route, seats=15):
        self.colour = colour
        self.route = route

inbound = Kombi(colour="yellow", route="Soweto → CBD")
loading  = Kombi(colour="blue",  route="Mamelodi run")

inbound.hooter()   # "Phiphi! 🚐"
inbound.route      # "Soweto → CBD"

Where they live: game characters, GUI widgets, Django models, user accounts — anywhere real-world 'things' with state and behaviour exist.

The story, slowly 🧠

1

Blueprint vs kombi

The class is the paper plan: seats, hooter, route slot. The paper itself can't drive anywhere. The plan must be brought to life.

2

Instantiate = build

Kombi(...) uses the blueprint to build a real kombi. Now it exists on the road with its own colour and route.

3

Each object is its own

Two kombis from the same blueprint are independent. Paint one blue, change the other's route — they don't affect each other.

4

State + behaviour

Attributes are what it has; methods are what it does. That pairing — data and action living together — is the whole point of OOP.
